# 11 — خارطة طريق التنفيذ الموصى بها
# Recommended Implementation Roadmap

تُرتَّب هذه الخطة إلى **5 مراحل متسلسلة** حسب الخطورة (`CRITICAL -> HIGH -> MEDIUM`)، الاعتماديات المعمارية، وأثر الإطلاق الإنتاجي الفعلي.

---

## المرحلة 0: إيقاف النزيف — طوارئ السلامة المحاسبية والأمنية (Production Blockers)
**الهدف:** سد الثغرات الحرجة التي تفسد الأرصدة أو تسمح بتجاوز الصلاحيات قبل أي تشغيل مالي حي.

1. **إصلاح دورة قيود الفوترة والتحصيل (`DEF-01`, `DEF-02`, `DEF-04`):**
   - استدعاء `DoubleEntryService` عند إصدار الفاتورة (`POST /bookings/hold`) أو عند التحويل إلى التزام تعاقدي (`Contract Liability / Deferred Revenue`) وفقاً للسياسة المعتمدة، ثم الاعتراف بالإيراد (`4000`/`4100`) وضريبة المخرجات (`2200`) في GL.
   - توحيد نقطة التحقق من الأقساط (إزالة التضارب بين `finance.py` و`lifecycle_ops.py`)، وإضافة `SELECT ... FOR UPDATE` + `idempotency_key` + فحص `milestone.status != "PAID"` لمنع الترحيل المزدوج.
   - إزالة `await db.commit()` من داخل `DoubleEntryService.post_balanced_entry` والاكتفاء بـ `flush()` حتى تتم العملية بأكملها في معاملة ACID واحدة ذرية.
   - في `ApprovalsService.resolve_approval`: توزيع `financial_delta + incremental_tax` على الأقساط (أو إنشاء قسط تعديل جديد إذا كانت مسددة) مع ترحيل قيد تسوية تلقائي في GL.
2. **سد ثغرات التفويض والوصول (`DEF-05`, `DEF-07`, `DEF-08`):**
   - التحقق الصارم في `resolve_approval` من أن `auth.user` يطابق `required_approver_role` (العميل الأساسي للفعالية لـ `CLIENT_PRIMARY`، ومدير العمليات/المالك لـ `OPS_MANAGER`).
   - فرض فحص ملكية الفعالية (`Event.primary_client_id` أو `EventDelegate` مع فحص `permissions`) على كافة مسارات `/portal/events/{id}/...`, `/events/{id}/drafts`, `/events/{id}/messages`, `/portal/audit-logs`, `/exports/invoices/{id}/pdf`.
   - حماية `/uploads/receipts` عبر endpoint مصادق عليه ومفحوص حسب `tenant_id` وملكية الفعالية، وتأمين رفع الإيصالات العام برمز مؤقت موقّع (`signed upload token`) يصدره الحجز فقط.
   - احتساب أسعار `addons` في `bookings.py` من جدول `InventoryItem` في قاعدة البيانات حصراً، وإزالة كلمة المرور الافتراضية `"Client@2026"` واستبدالها بتوليد رابط تفعيل/OTP.
3. **إصلاح خصم الأضرار ورد التأمين و`EventExpense` (`DEF-03`, `DEF-06`):**
   - إنشاء قسط مخصص أو مسار تحصيل واضح للتأمين (`2100`).
   - عند `DAMAGE_CLAIMED`: ترحيل `Dr 2100 / Cr Damage Recovery`. وإضافة endpoint/شاشة لرد التأمين (`REFUNDED`: `Dr 2100 / Cr 1010/1020`).
   - إضافة CRUD API وشاشة لإدخال مصروفات الفعالية (`EventExpense`) مع ترحيلها لـ GL.

## المرحلة 1: استكمال النواة المحاسبية والأستاذ العام والرقابة الداخلية
**الهدف:** جعل دفتر الأستاذ العام قابلاً للاعتماد والعمل المحاسبي اليومي.

1. **تطوير نموذج دليل الحسابات (`ChartOfAccount`) و`AccountingConfig`:**
   - إضافة `parent_id`, `level`, `is_group`, `normal_balance` (`DEBIT`/`CREDIT`), `is_control_account`, وربط FK لـ `AccountingConfig` وإضافة حسابات حقوق الملكية (`3000`, `3100`) والذمم الدائنة (`2000`) والإيرادات المؤجلة (`2300`) والمصروفات التشغيلية.
   - إضافة واجهة API (`PATCH/ARCHIVE`) وشاشة كاملة لإدارة دليل الحسابات وإعدادات الحسابات الافتراضية والضريبة.
2. **استكمال محرك الأستاذ العام (`GL`):**
   - تسلسل رقمي متتابع آمن (`Gapless Sequence Table` لكل مستأجر وسنة مالية) لـ `JE-`, `INV-`, `EVT-`.
   - إضافة حالة مسودة واعتماد للقيود (`DRAFT -> PENDING_APPROVAL -> POSTED -> REVERSED`) مع فصل المهام (`created_by_id != approved_by_id`).
   - بناء آلية القيود العكسية (`POST /finance/journal-entries/{id}/reverse` مع `reversed_entry_id`) ومنع `UPDATE/DELETE` على القيود المرحلة عبر Trigger في PostgreSQL.
   - بناء تقرير **دفتر الأستاذ التفصيلي (`Account Ledger`)** بالرصيد التراكمي وفلاتر التاريخ والعملة وربط `Drill-down` للمستند الأصلي.
   - تصحيح `Trial Balance` ليربط بـ `JournalEntry.status == "POSTED"` ويحترم `normal_balance` وفلاتر التاريخ.
3. **بناء السنوات والفترات المالية والإقفال (`Domain K`):**
   - إنشاء `FiscalYear` و`AccountingPeriod` (شهري) مع حالات `OPEN | LOCKED | CLOSED` وفرض تحقق صارم في محرك الترحيل يمنع الترحيل في فترة مقفلة.
4. **تثبيت الحجوزات والمخزون (`DEF-09`, `DEF-10`, `DEF-15`):**
   - قفل صف القاعة (`SELECT ... FOR UPDATE`) أو قيود استبعاد PostgreSQL لمنع Double-Booking، وخصم/حجز `EventInventoryAllocation` عند الحجز، وإلغاء الفاتورة (`VOIDED`) في مهمة انتهاء 48h، ونقل `_OTP_STORE` إلى Redis والتحقق من توقيع WhatsApp HMAC.

## المرحلة 2: القوائم المالية المعيارية والتقارير والضرائب
**الهدف:** توفير قوائم مالية موثوقة متوافقة مع IAS 1 / IAS 7 / IFRS 15.

1. **القوائم المالية الأربعة:**
   - قائمة المركز المالي (`Balance Sheet`)
   - قائمة الدخل الشاملة (`Income Statement`)
   - قائمة التدفقات النقدية (`Cash Flow Statement`)
   - قائمة التغير في حقوق الملكية (`Statement of Changes in Equity`)
   - مع دعم الفترات المقارنة والتصدير لـ `.xlsx` وPDF نظيف بدون fallback صامت.
2. **تقارير الذمم والضرائب:**
   - إشعارات دائنة ومدينة (`Credit/Debit Notes`) لـ AR.
   - أعمار الديون (`AR Aging`) وكشف حساب العميل (`Customer Statement`)، ومخصص الديون (IFRS 9).
   - وحدة الضرائب المحدثة (ضريبة مخرجات/مدخلات، نسب مؤرخة، إقرار ضريبي، طباعة `tax_id` في الفاتورة PDF).
3. **إقفال نهاية العام (`Year-End Closing`):**
   - قيد إقفال آلي لحسابات الإيرادات والمصروفات إلى الأرباح المحتجزة (`3100`) وميزان المراجعة بعد الإقفال.

## المرحلة 3: الذمم الدائنة والبنوك والأصول الثابتة وتعدد العملات
**الهدف:** تغطية دورة المصروفات والأصول والنقدية كاملة لتتحول المنصة إلى ERP متكامل.

1. **الذمم الدائنة والمشتريات (`AP`):** الموردون، أوامر الشراء، استلام البضائع، فواتير الموردين، المطابقة الثلاثية، سندات الصرف، وأعمار AP.
2. **إدارة البنوك والتسوية (`Cash & Bank`):** ربط كل بنك/محفظة (كريمي، جيب، جوالي، ون كاش) بحساب GL فرعي، استيراد كشوف البنك، المطابقة الآلية/اليدوية، العهد النقدية، والشيكات.
3. **الأصول الثابتة (`Fixed Assets`):** سجل أصول القاعات والمعدات، طرق الإهلاك (IAS 16)، ترحيل الإهلاك الشهري الآلي، الاستبعاد والصيانة.
4. **تعدد العملات (`Multi-Currency` - IAS 21):** عملة أساسية ووظيفية، جدول أسعار صرف مؤرخ، معالجة `YER/SAR/USD` على الفواتير والقيود، وإعادة التقييم وفروق العملة.

---

## المرحلة 4: محاسبة التكاليف المتقدمة، الموازنات، التوحيد، والاختبارات الشاملة
1. **التكاليف والموازنات:** مراكز تكلفة لكل قاعة وقسم، ربط `CateringMenuItem.recipe_bom` بتكلفة المكونات الفعلية (IAS 2)، توزيع التكاليف غير المباشرة، عمولات الموظفين، والموازنات مع الرقابة والانحرافات.
2. **التوحيد المالي (عند الحاجة لمجموعات القاعات):** شركات متعددة، معاملات بينية، واستبعاد.
3. **مجموعة اختبارات مالية وأمنية شاملة:** اختبارات على PostgreSQL الحقيقي تشمل التزامن (`asyncio.gather`)، منع التكرار، التراجع الذري، فحص IDOR/SoD، واختبارات Playwright E2E للواجهات المالية.
